## 1. 가격이 갑자기 튀는 데이터

**증상**
어떤 상품의 평균 가격이 특정 조사일에만 갑자기 크게 오르거나 내려가서, 등락률과 그래프가 실제와 다르게 나왔습니다.

**원인**
어떤 상품은 평소 매장 수가 많은데(예: 180개), 특정 조사일에만 조사 매장이 크게 줄어드는 경우(예: 18개)가 있었습니다.
그 시점의 평균은 가격이 변한 것이 아니라 **조사한 매장이 바뀌어서** 달라진 값(표본 노이즈)이었습니다.

**시도 1 (실패)**
"매장 수가 20개 미만이면 무조건 제외"하는 **절대 기준**을 적용했습니다.
그러자 갈치, 깻잎, 오징어처럼 **원래 4~13개 매장에서만 조사되는 신선식품(약 30개 상품)이 통째로 사라졌습니다.**
이런 상품은 매번 비슷한 규모로 조사되기 때문에 평균을 비교해도 노이즈가 아닌데, 기준이 너무 거칠었던 것입니다.

**해결**
상품마다 평소 매장 수(중앙값)를 구하고, 그 **30% 미만**인 조사 시점만 제외하는 **상대 기준**으로 바꿨습니다. (`min_ratio_vs_median=0.3`)
이 기준으로 노이즈로 판단된 조사 시점 402건이 제외되었고, 원래 매장이 적은 상품은 그대로 유지됩니다.
집계 로직을 `aggregation.py` 한 곳에 모아서 분석, 예측, DB 적재가 모두 같은 기준을 쓰도록 했습니다.

**배운 점**
데이터를 걸러낼 때는 하나의 고정 숫자보다 **그 데이터의 평소 규모와 비교하는 기준**이 더 안전합니다. 기준을 정한 뒤에는 사라지는 데이터가 없는지도 확인해야 합니다.

## 2. 카테고리 자동 분류가 부정확함

**증상**
원본 데이터에는 카테고리 정보가 없어서 상품명의 키워드로 자동 분류했는데, 한국소비자원의 실제 분류와 많이 달랐습니다.

**원인**
상품명의 키워드만으로는 분류가 애매한 경우가 많았습니다.

**해결**
- 상품 510개를 공식 13개 분류로 하나씩 확인해서 **정답표(`category_mapping.csv`)** 를 직접 만들었습니다.
- 정답표에 있는 상품은 그대로 사용하고, **정답표에 없는 새 상품만 키워드 규칙으로 임시 분류**하도록 `categorize.py` 를 바꿨습니다.
- 새로 분류된 상품은 검토한 뒤 정답표에 추가하면 다음부터는 정답표 기준으로 처리됩니다.

**배운 점**
자동 규칙은 처음 보는 데이터를 위한 **보조 수단**으로 두고, 이미 확인한 데이터는 사람이 검증한 값을 쓰는 편이 정확합니다.

## 3. 그래프가 변동을 과장해서 보임

**증상**
가격 차이가 몇 원밖에 안 되는 상품인데도 상세 페이지의 그래프가 크게 출렁이는 것처럼 보였습니다.

**원인**
matplotlib 은 데이터의 최솟값~최댓값에 맞춰 Y축 범위를 자동으로 좁게 잡습니다.
그래서 5,253원과 5,258원처럼 작은 차이도 그래프 전체 높이를 쓰게 되어 변동이 과장되어 보였습니다.

**해결**
`(최고가 - 최저가) / 최저가` 가 **30% 미만**이면 변동이 작은 상품으로 보고 **Y축을 0부터** 그리도록 했습니다. (`VARIATION_THRESHOLD = 0.3`)
- 변동이 작은 상품(예: Dole 파인애플 슬라이스)은 거의 평평한 선으로 보입니다.
- 변동이 큰 상품(예: 크리넥스 클린케어)은 기존처럼 움직임이 그대로 보입니다.

**배운 점**
같은 데이터도 축을 어떻게 잡느냐에 따라 전달되는 인상이 달라집니다. 그래프는 **실제 변동 폭이 그대로 느껴지도록** 그려야 합니다.

## 4. PostgreSQL 에서 `nan원` 이 표시됨

**증상**
전년동기 대비 랭킹에서 순위 맨 위에 **`nan원`** 이 표시되었습니다. PostgreSQL 에 데이터를 적재한 뒤에 나타났습니다.

**원인**
pandas 의 빈 값(`NaN`)을 그대로 DB 에 넣었는데, PostgreSQL 은 NaN 을 빈 값(NULL)이 아니라 **실제 숫자 값**으로 저장합니다.

- 정렬하면 NaN 이 가장 큰 값으로 취급되어 순위 맨 위로 올라왔고, "값이 있음(`IS NOT NULL`)" 조건도 통과했습니다.
  전년동기 비교는 1년 전 자료가 없는 상품이 많아서 NaN 이 많았기 때문에 눈에 띄었습니다.

**해결**
`load_to_db.py` 에 NaN 을 NULL 로 바꾸는 함수를 추가하고, 비어 있을 수 있는 6개 컬럼(이전가격, 차액, 등락률, 전년동기가격, 전년동기차액, 전년동기등락률)을 저장할 때마다 적용했습니다.

```python
def _clean(value):
    """pandas의 NaN(값 없음)을 DB의 NULL(None)로 바꾼다. 아니면 일반 숫자로 변환."""
    return None if pd.isna(value) else float(value)
```

수정한 뒤 DB 를 다시 적재(`uv run python -m services.load_to_db`)했고, 랭킹에서 `nan원` 이 사라진 것을 확인했습니다.
Docker 배포용 SQL 내보내기(`export_db_sql.py`)에서도 NaN 은 NULL 로 내보냅니다.

**배운 점**
pandas 의 NaN 과 DB 의 NULL 은 다르며, **DB 마다 처리 방식이 다릅니다.** 데이터를 적재한 뒤에는 실제 쓸 DB 에서 정렬과 NULL 조건 결과를 직접 확인해야 이런 문제를 미리 발견할 수 있습니다.

## 마무리

문제를 풀면서 공통으로 느낀 점은 다음과 같습니다.

1. **데이터는 그대로 믿지 않고 먼저 의심해 본다.** (표본 노이즈, 분류 정확도, 그래프 착시)
2. **개발 환경과 실제 환경의 차이를 확인한다.** (pandas 의 NaN 과 PostgreSQL 의 NULL)
3. **기준을 정했으면 그 기준으로 사라지는 것이 없는지 검증한다.**
