## 1. GitHub Actions에서 AI 분석 테스트 실패

### 현상

GitHub Actions에서 `pytest` 테스트를 실행했을 때 **28개 테스트 중 1개가 실패**했다. 실패 항목은 다음과 같았다.

```text
tests/test_ai.py::test_process_meeting_ai
```

### 원인

AI 분석 서비스의 구현이 기존 Gemini 클라이언트 호출 방식에서 **OpenAI API 호출 방식**으로 변경되었지만, 테스트의 모킹(mocking) 코드는 이전 구조를 기준으로 작성되어 있었다.

- 기존 테스트의 모킹 대상: `mock_client.models.generate_content`
- 실제 서비스의 호출 구조: `client.chat.completions.create(...)`
- 실제 응답 내용 접근 방식: `response.choices[0].message.content`

즉, 서비스 코드와 테스트 더블(mock 객체)의 인터페이스가 일치하지 않았다.

### 해결 과정

1. `services/ai_service.py`의 실제 API 호출 구조를 확인했다.
2. `tests/test_ai.py`의 모킹 대상을 OpenAI 클라이언트 구조에 맞게 수정했다.
3. 테스트 응답 객체도 `choices[0].message.content` 구조에 맞춰 수정했다.
4. 수정한 테스트 파일을 Docker 컨테이너에 반영하고 전체 테스트를 재실행했다.
5. 변경 사항을 GitHub에 커밋·푸시하여 GitHub Actions 결과를 다시 확인했다.

### 검증 결과

Docker 컨테이너에서 다음 명령으로 전체 테스트를 실행했다.

```bash
docker exec -w /app meetflow_api python -m pytest -v
```

확인된 결과:

```text
28 passed, 1 warning in 4.21s
```

이후 GitHub Actions에서도 성공 결과를 확인했다.

### 배운 점

외부 AI SDK 또는 서비스 구현을 변경하면 **단위 테스트의 모킹 구조도 함께 갱신**해야 한다. 테스트가 실패했을 때 실제 비즈니스 로직의 오류인지, 테스트가 이전 인터페이스를 가정한 것인지 구분하는 과정이 중요했다.

## 2. JWT 인증 적용 후 API 접근 및 사용자별 데이터 처리 점검

### 현상

인증 기능을 구현하는 과정에서 보호된 API에 접근할 때 인증 토큰 유무에 따라 응답이 달라졌다. 프로젝트 목록 API는 로그인 사용자에게 허용된 프로젝트만 반환하도록 구현해야 했다.

### 원인 및 점검 사항

JWT (JSON Web Token) 인증을 사용하는 API는 단순히 로그인 기능만 구현하는 것으로 충분하지 않다. 요청에서 토큰을 읽고 사용자 정보를 확인한 뒤, 해당 사용자가 조회·수정하려는 데이터에 접근할 권한이 있는지 검증해야 한다.

### 해결 과정

1. 로그인 API와 JWT 발급·검증 로직을 구현했다.
2. Swagger의 인증 기능을 이용하여 토큰을 포함한 요청을 테스트했다.
3. 사용자별 프로젝트 목록 조회에 인증된 사용자 기준의 필터링을 적용했다.
4. 프로젝트 소유자 정보(`owner_id`)가 필요한 응답에서 올바르게 표시되는지 점검했다.

### 검증 결과

개발 중 확인한 대표적인 동작:

- 인증 토큰이 없는 보호 API 요청: **401 Unauthorized**
- 유효한 인증 토큰을 포함한 요청: **200 OK**
- `GET /projects/`: 로그인한 사용자 기준의 프로젝트 목록 반환 확인
- 프로젝트 소유자 정보 표시 문제 수정 후 정상 출력 확인

### 배운 점

**인증(Authentication)**과 **인가(Authorization)**는 별개다. 토큰으로 사용자를 식별하는 것과, 그 사용자에게 특정 프로젝트·회의에 접근할 권한이 있는지 확인하는 작업을 분리하여 점검해야 한다.

## 3. 프로젝트·회의 공유 및 참여자 식별 문제

### 현상

여러 사용자가 프로젝트와 회의를 공유하는 기능을 구현하면서 다음 항목을 점검해야 했다.

- 공유 계정에서 회의 목록이 예상대로 표시되는지
- 프로젝트 소유자와 참여자의 접근 권한이 올바르게 구분되는지
- 조회 권한만 있는 사용자가 수정·삭제 기능을 사용할 수 없는지
- **동명이인**이 있을 때 참여자를 정확하게 식별할 수 있는지

### 원인 및 설계상 쟁점

프로젝트 참여와 개별 회의 참여는 범위가 다르므로, 프로젝트 공유 여부만으로 모든 회의의 접근 권한을 결정하면 실제 요구사항과 어긋날 수 있다. 또한 화면에 이름만 표시하면 같은 이름을 가진 계정을 구별하기 어렵다.

### 해결 및 개선 과정

1. 프로젝트 공유 정보와 회의별 참여자 정보를 구분하여 관리하도록 설계를 확장했다.
2. 회의 참여자 관리에 `meeting_participants` 구조를 반영했다.
3. 참여자 선택·표시 시 이름 외에 이메일 정보를 함께 활용하여 동명이인을 구별하도록 개선했다.
4. 회의 조회 및 수정·삭제 기능에서 사용자 권한을 점검했다.

### 확인된 결과 및 추가 검증 항목

회의별 참여자 관리 및 이메일 표시 기능이 프로젝트에 반영되었다. 다만 **모든 권한 조합에 대한 자동 테스트 통과 여부는 별도 확인이 필요**하므로, 최종 시연 전 아래 시나리오를 점검하는 것이 좋다.

- 소유자 / 공유 참여자 / 비참여자별 회의 조회
- 조회 전용 사용자에 대한 수정·삭제 제한
- 이름이 같은 두 계정의 참여자 선택

### 배운 점

다중 사용자 서비스에서는 화면에 보이는 이름과 실제 계정 식별자를 혼동하면 안 된다. 데이터베이스의 사용자 ID를 기준으로 권한을 판단하고, 화면에서는 이메일 등 보조 정보를 제공하는 것이 중요하다.

## 4. Docker 환경에서 데이터베이스 연결 주소 구분

### 현상

로컬 실행 환경과 Docker Compose 환경에서 PostgreSQL 연결 주소를 동일하게 사용하면 접속 문제가 발생할 수 있어 설정을 구분해야 했다.

### 원인

Docker 컨테이너 내부의 `localhost`는 개발자 PC나 다른 컨테이너가 아니라 **해당 컨테이너 자신**을 의미한다. 따라서 FastAPI 컨테이너가 PostgreSQL 컨테이너에 접근하려면 Compose 서비스 이름인 `db`를 호스트로 사용해야 한다.

### 적용한 해결 방식

`docker-compose.yml`의 API 서비스에 컨테이너 전용 연결 문자열을 설정했다.

```yaml
environment:
  DATABASE_URL: postgresql+psycopg://${POSTGRES_USER}:${POSTGRES_PASSWORD}@db:5432/${POSTGRES_DB}
```

또한 DB 준비 상태를 확인한 뒤 API가 시작되도록 구성했다.

```yaml
depends_on:
  db:
    condition: service_healthy
```

DB 서비스에는 `pg_isready` 기반 상태 검사를 설정했다.

### 검증 방법

```bash
docker compose ps
```

```bash
docker compose logs api
```

현재 Compose 파일에 해당 설정이 반영되어 있는 것은 확인되었다. 이 항목은 **구성상 문제를 예방한 사례**로, 당시의 구체적인 연결 실패 로그나 수정 전후 시각은 확인되지 않아 기재하지 않았다.

### 배운 점

Docker Compose에서 컨테이너 간 통신에는 서비스 이름을 사용해야 한다. 또한 컨테이너가 실행 중이라는 사실과 데이터베이스가 실제로 연결 가능한 상태라는 사실은 다르므로 상태 검사가 유용하다.

## 5. 최종 제출 환경변수 예시 파일 불일치 발견 및 수정

### 현상

최종 제출 점검 과정에서 `.env.example`에는 과거 Gemini API 설정이 남아 있었고, `docker-compose.yml`이 요구하는 PostgreSQL 변수는 누락되어 있었다.

### 원인

개발 도중 AI 서비스가 OpenAI API 기반으로 변경되었지만, 예시 환경설정 파일이 최신 구현을 반영하지 못했다.

### 해결 과정

1. `services/ai_service.py`에서 `OPENAI_API_KEY`, `OPENAI_AI_MODEL` 사용을 확인했다.
2. `services/stt_service.py`에서 `OPENAI_STT_MODEL`, `UPLOAD_DIR`, `MAX_AUDIO_MB` 사용을 확인했다.
3. `docker-compose.yml`에서 `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` 사용을 확인했다.
4. `.env.example`을 수정하여 최신 환경변수와 **실제 비밀정보가 아닌 예시 값**을 기재했다.

### 검증 결과

소스코드와 Docker Compose가 참조하는 환경변수 이름을 대조하고 예시 파일을 갱신했다. 수정된 파일을 이용한 **신규 환경에서의 재설치 성공 여부는 아직 별도 검증하지 않았다**.

### 배운 점

환경설정 예시 파일은 단순 참고 자료가 아니라 다른 개발자가 프로젝트를 재현하는 데 필요한 문서다. 외부 API나 컨테이너 설정이 바뀌면 `.env.example`도 함께 갱신해야 한다.
